# Software Engineering Concepts

## Software Development Life Cycle
SDLC defines stages for developing software. Waterfall: linear sequential phases (requirements, design, implementation, testing, deployment, maintenance). Simple but inflexible. Agile: iterative and incremental development in sprints. Adapts to changing requirements. Scrum: Agile framework with sprints (2-4 weeks), daily standups, sprint planning, sprint review, retrospective. Roles: Product Owner (defines requirements), Scrum Master (facilitates process), Development Team. Kanban: visual workflow management with cards and columns (To Do, In Progress, Done). Limits work-in-progress. V-Model: testing phase for each development phase. Spiral: combines iterative development with systematic risk assessment.

## Agile and Scrum Deep Dive
Agile Manifesto values: individuals over processes, working software over documentation, customer collaboration over contract negotiation, responding to change over following a plan. User Stories: "As a [user], I want [feature] so that [benefit]." Acceptance criteria define when a story is done. Story points estimate relative effort. Sprint Planning: team selects stories from the product backlog for the sprint. Daily Standup: 15-minute meeting answering what did I do yesterday, what will I do today, any blockers. Sprint Review: demonstrate completed work to stakeholders. Sprint Retrospective: what went well, what to improve, action items. Velocity: average story points completed per sprint, used for planning.

## Design Principles
SOLID Principles: S - Single Responsibility (a class should have one reason to change). O - Open/Closed (open for extension, closed for modification). L - Liskov Substitution (subclasses should be substitutable for base classes). I - Interface Segregation (many specific interfaces over one general interface). D - Dependency Inversion (depend on abstractions, not concretions). DRY: Don't Repeat Yourself, avoid code duplication. KISS: Keep It Simple. YAGNI: You Aren't Gonna Need It, don't build features not yet required. Separation of Concerns: divide program into distinct sections, each handling a specific aspect.

## Testing Concepts
Unit Testing: test individual functions or methods in isolation. Mock external dependencies. Use assertions to verify expected behaviour. Integration Testing: test how modules work together. Test API endpoints with database. End-to-End Testing: simulate real user flows through the entire application. Test-Driven Development (TDD): write tests first, then write code to pass tests, then refactor. Red-Green-Refactor cycle. Behaviour-Driven Development (BDD): describe behaviour in plain language (Given-When-Then). Code Coverage: percentage of code executed by tests. 80% is a common target. Testing Pyramid: many unit tests (fast, cheap), fewer integration tests, fewest E2E tests (slow, expensive). Regression Testing: ensure new changes do not break existing functionality.

## API Testing
Test API endpoints with tools like Postman, Insomnia, or automated test frameworks. Test categories: functional (correct responses for valid inputs), negative (proper error handling for invalid inputs), boundary (edge cases like empty strings, max length, zero values), authentication (protected routes return 401 without token), authorization (users cannot access other users' data), performance (response time under load). HTTP status code testing: verify correct status codes for each scenario. Response body testing: verify JSON structure and data types. Test CRUD operations: create, read, update, delete. Automated API tests can be written with Jest, Mocha, Supertest for Node.js applications.

## Code Quality
Clean code: meaningful variable and function names, small functions that do one thing, consistent formatting, no magic numbers (use named constants), minimal nesting, proper error handling. Code smells: long methods, god classes, duplicate code, dead code, excessive comments explaining bad code. Refactoring: improve code structure without changing behaviour. Extract method, rename variable, move function, simplify conditionals. Technical debt: shortcuts taken now that will cost more to fix later. Manage by allocating time for refactoring in each sprint. Code reviews: systematic examination of code by peers. Catches bugs, improves quality, shares knowledge. ESLint for JavaScript, Pylint for Python enforce coding standards automatically.

## Documentation
Types of documentation: README (project overview, setup instructions, usage), API documentation (endpoints, request/response formats, authentication), architecture documentation (system design, component diagrams), code comments (explain why, not what), changelogs (what changed in each version), user guides (how to use the product). Good README includes: project description, features, tech stack, installation steps, environment variables, API endpoints, screenshots, contributing guidelines. API documentation tools: Swagger/OpenAPI, Postman documentation. Keep documentation updated with code changes. Write documentation as you develop, not as an afterthought.

## Version Control Best Practices
Commit messages: use present tense ("Add login API" not "Added login API"). Start with a verb. Keep first line under 72 characters. Add detailed description if needed. Commit frequently with logical, atomic changes. One commit per logical change. Branch naming: feature/feature-name, bugfix/bug-description, hotfix/urgent-fix. Pull request checklist: code compiles, tests pass, no linting errors, documentation updated, screenshots for UI changes. Protect main branch: require PR reviews, require passing CI, no direct pushes. Tag releases with semantic versioning: MAJOR.MINOR.PATCH (breaking.feature.fix). Git hooks: pre-commit (lint, format), pre-push (run tests).

## Security Best Practices
Input validation: validate all user inputs on both client and server. Never trust client-side validation alone. SQL injection prevention: always use parameterised queries, never concatenate user input into SQL strings. XSS prevention: sanitise user-generated content, use Content-Security-Policy headers, encode output. CSRF prevention: use CSRF tokens for state-changing requests. Authentication: hash passwords with bcrypt (salted, computationally expensive), use JWT with appropriate expiration, implement refresh tokens. Rate limiting: prevent brute force attacks. HTTPS: encrypt all communication. Environment variables: never commit secrets to version control. CORS: configure allowed origins specifically, not wildcard in production. Dependency security: regularly update packages, use npm audit to find vulnerabilities.
